# Generated code in OAI NEF

**Most of the C++ that NEF compiles is machine-generated and must not be hand-edited.** It lives
inside a submodule, it outweighs NEF's own source by a factor of about 35, and it is
committed rather than produced by the build.

Read this page before you edit anything under `src/common-src/`, and in particular before you
reach for a regeneration. It covers which directories are generated, how NEF selects the subset it
compiles, what the generator inputs are, and — honestly — what is not known about reproducing any
of it.

If you are here because of a specific symptom, the short answers are:

- **Undefined reference to a model class at link time** — §3. The class is not in
  `nef_model.cmake`.
- **A model class is wrong or missing a field** — §5, then §7. The fix goes in the submodule
  repository, not here.
- **You are about to regenerate the models** — §5 and §6, in that order.

---

## 1. Scale

The numbers are the reason for the rest of this page: generated code is not a corner of this tree,
it is the bulk of it.

| | Hand-written NEF source (`src/`, excluding `common-src`) | Generated 3GPP models (`src/common-src/model/`) |
|---|---:|---:|
| Files | 53 `.cpp`/`.hpp`/`.h` | 3,844 `.cpp`/`.h` (1,918 + 1,926) |
| Lines | ~15,700 | 560,702 |

`src/common-src/model/` additionally holds 12 `.cmake` fragments — one curated source list per
network function (`nef_model.cmake`, `amf.cmake`, `smf_model.cmake`, …). They are hand-maintained
build files, not generated code.

## 2. What is generated, and where

The submodule holds three quite different kinds of code, and only the first is generated output
that NEF compiles.

### 2.1 `src/common-src/model/` — the 3GPP OpenAPI model classes

3,829 of the 3,844 files carry the banner:

```
NOTE: This class is auto generated by OpenAPI Generator
(https://openapi-generator.tech). https://openapi-generator.tech Do not edit
the class manually.
```

Each class is a 3GPP data type with `to_json` / `from_json` free functions and a `validate()`
method. NEF consumes them through ADL — `from_json(body, req_data)` is called **unqualified**
throughout `src/nef_app/`, so any regeneration that namespace-qualifies or renames those free
functions breaks every call site silently at overload-resolution time, not at the declaration.

**Fifteen files in that directory have no generator banner**, so they are hand-written or
hand-edited and a blind regeneration would destroy them. Two of them are in NEF's compiled set:

| File | Used by |
|---|---|
| `UserPlaneEvent.cpp` / `.h` | included by `nef_app_core.cpp`; listed in `nef_model.cmake` |
| `UserPlaneEvent_anyOf.cpp` / `.h` | same |

Re-derive the list at any time with:

```bash
for f in $(find src/common-src/model -name '*.h' -o -name '*.cpp'); do
  grep -ql "OpenAPI Generator" "$f" || echo "$f"
done
```

### 2.2 `src/common-src/ngap/` — asn1c output

2,428 files of ASN.1-compiler output. **NEF does not compile any of it**: nothing under `src/`
outside the submodule references `ngap`, and no `.cmake` fragment NEF includes pulls it in. It is
present because the submodule is shared with the AMF.

### 2.3 Everything else in the submodule

`src/common-src/{common,config,logger,sba,utils,3gpp}` is hand-written shared OAI source. NEF
compiles it via the `.cmake` fragments included from `src/oai-nef/CMakeLists.txt`. It is not
generated — but it is still **out of bounds for this repository**, because it is a submodule
shared with the other network functions. Changes there belong in
`github.com/openairinterface/oai-cn5g-common-src`.

## 3. Which models NEF actually compiles

Compiling 1,918 model `.cpp` files would dominate the build. NEF compiles **431** of them, and the
list of which 431 is maintained by hand.

The selection lives in `src/common-src/model/nef_model.cmake` (452 lines), which describes itself
at the top of the file:

> Only the model classes actually reachable from NEF sources are compiled (computed as the
> transitive `#include` closure of NEF's translation units). This is the curated equivalent of
> `USED_*_MODEL_SRC_FILES` and keeps the build fast instead of compiling every generated model.
> Regenerate when NEF starts using new models.

Mechanically: the fragment sets `NEF_MODEL_SRC_FILES` to those 431 paths and, when `NF_TARGET` is
defined, adds them to that target's sources. It is `include()`d twice — once by
`src/oai-nef/CMakeLists.txt` for the `oai_nef` executable, and once by `test/CMakeLists.txt` for
the test targets that need typed models.

**If you add a `#include` of a model class that is not in that list, the build fails at link
time with an undefined reference, not at compile time.** The header is there, so the compile
succeeds; only the definition is missing. The fix is to add the `.cpp` to `nef_model.cmake` —
together with anything *it* includes transitively.

Count them with:

```bash
grep -cE '^\s+\$\{NEF_MODEL_DIR\}/' src/common-src/model/nef_model.cmake
```

## 4. The generator inputs: `3gpp_specs/`

The specs the models were generated from are committed at the repository root, along with the
generator jar itself. What is *not* committed is how they were combined — see §5.

135 entries:

| | |
|---|---|
| 133 `.yaml` | 3GPP OpenAPI documents; the largest groups are `TS29522_*` (25), `TS26512_*` (17), `TS29122_*` (16) and `TS29222_*` (11) |
| `openapi-generator-cli-7.11.0.jar` | the OpenAPI Generator CLI, version 7.11.0 |
| `config.json` | two keys: `{"modelPackage": "oai::model", "apiPackage": "oai::api"}` |

That is the whole directory. There is **no `.openapi-generator-ignore`**, no template directory,
and no record of which YAMLs were fed in or in what order.

## 5. How to regenerate: **UNKNOWN**

This section deliberately does not give you a command, because the tree does not contain one and
guessing would be worse than saying nothing. **The original generator invocation is UNKNOWN.**

**What is established:**

* The generator was **OpenAPI Generator CLI 7.11.0** (the jar is committed).
* The configuration was, at minimum, `modelPackage = oai::model` and `apiPackage = oai::api`.
* The inputs were the 3GPP OpenAPI YAMLs now sitting in `3gpp_specs/`.
* The output is committed to the `src/common-src` submodule, not to this repository.

**What is not established, and is not recoverable from this tree:**

* The exact command line — generator name (`cpp-pistache-server`? `cpp-restsdk`? something
  custom?), `--template-dir`, `--global-property`, per-file vs per-spec invocation.
* Whether the templates were stock or modified. The output does not match any stock generator
  exactly: it uses `nlohmann::json` free functions and a `helpers::ValidationException`, and the
  fifteen unbannered files show that post-generation editing happened at least once.
* Whether the 133 YAMLs were run individually and merged, or resolved as one document set.
* The order in which conflicts between overlapping specs were resolved.

**Nothing in the build invokes the jar.** Verified repository-wide:

```bash
grep -rn "openapi-generator" --include='*.sh' --include='*.cmake' \
     --include=CMakeLists.txt --include='*.py' --include='*.yml' .
```

returns no invocation. There is no CMake codegen step, no script, and no CI stage. Regeneration,
if it ever happened here, was a manual act that left no trace.

**Practical consequence:** treat `src/common-src/model/` as a vendored binary artefact. If a model
class is wrong or missing, the supported path is to change it in the
`oai-cn5g-common-src` repository — carefully, one class at a time — and bump the submodule
pointer. Do not attempt a bulk regeneration on the basis of this page; you would first have to
reconstruct the invocation, and then reconcile 3,844 files against fifteen hand-edits you may not
find until runtime.

## 6. Constraints any regeneration would have to preserve

If someone does reconstruct the invocation, these are the properties NEF depends on. Each is
verifiable in the current tree; none is enforced by a test, so a regeneration that breaks one of
them will show up as a runtime surprise rather than a failed build.

| # | Constraint | Where it bites |
|---|---|---|
| 1 | `from_json` / `to_json` stay **unqualified free functions** found by ADL | every typed parse in `src/nef_app/nef_app_*.cpp` |
| 2 | `validate()` throws `oai::_3gpp::model::helpers::ValidationException` | 10+ catch sites; it is the **422** path |
| 3 | A malformed body raises `nlohmann::json::exception` | the same try blocks; it is the **400** path |
| 4 | `UserPlaneEvent` and `UserPlaneEvent_anyOf` are **not** stock generator output | they would be overwritten by a bulk regeneration (§2.1) |
| 5 | The T8 PFD wire keys `"applicationId"` and `"pfds"` keep their spelling | `nef_app_pfd.cpp` builds and reads them as raw JSON |
| 6 | `PfdSubscription` still needs the `notifUri` ↔ `notifyUri` adapter | `nef_app_pfd.cpp` normalises on the way in and reverses it on the way out, because the wire says `notifUri` and the model says `notifyUri`. If a regeneration renames the member, **remove the adapter**; if it does not, keep it |

### Typed versus raw stores

NEF's in-memory state is deliberately a mix of typed models and raw JSON, and the mix is
information, not inconsistency (`src/nef_app/nef_app.hpp`, private block):

| Store | Representation |
|---|---|
| `m_bdt_sessions` | typed `model::BdtPolicy` |
| `m_pfd_trans_sessions` | typed `model::PfdDataForApp` |
| `m_nnef_pfd_subscriptions` | typed `model::PfdSubscription` |
| `m_nnef_event_subscriptions` | typed `model::NefEventExposureSubsc` |
| `m_ti_sessions` | raw `nlohmann::json` |
| `m_nnef_pfd_transactions` | raw `nlohmann::json` |

The raw ones are raw on purpose: they round-trip AF-supplied bodies whose shape NEF does not fully
constrain. Converting them to typed models is a behavioural change — it would start rejecting
bodies that are accepted today — not a cleanup.

## 7. Submodule pinning

Three submodules, one of which carries everything discussed above.

| Submodule | Path | Supplies |
|---|---|---|
| `oai-cn5g-common-src` | `src/common-src` | the generated models **and** the shared `sba`/`config`/`logger`/`utils` sources |
| `oai-cn5g-common-build` | `build/common-build` | `build_helper`, CMake modules, third-party recipes including nghttp2 |
| `oai-cn5g-common-ci` | `ci-scripts/common` | shared CI helpers |

Two things about these pins have cost time before.

**The `.gitmodules` section name for the shared sources was renamed** from
`src/oai-cn5g-common-src` to `src/common-src`. Section names key `.git/modules/`, so an existing
clone silently keeps using the old path until it runs `git submodule sync --recursive`. A fresh
clone is unaffected.

**The pins are not always on their repository's default branch.** `git submodule update --init
--recursive` fetches by SHA and works regardless; a CI runner configured with `--depth 1`, or a
mirror that only tracks default branches, may not.

If a topic branch is ever deleted or force-pushed, the recorded SHA becomes unfetchable. The only
correct fix is to ask the submodule maintainer for a durable ref — a tag, or a merge into a
long-lived branch — and re-pin to that. Do **not** "fix" it by resetting the pin backwards: older
`common-src` revisions do not contain `model/` at all, and `src/oai-nef/CMakeLists.txt` fails at
`include(... common.cmake)` before a single file is compiled.
